# dsh-memory 全量 TypeScript 迁移方案（0.6.0 → 1.0.0）

结论：源码从 `lib/*.js` 整体搬到 `src/*.ts`，`lib/` 从此只放构建产物（tsdown，`outDir: lib`，关 clean），运行时入口、profile 按包名加载、83 个测试的 import 路径一律不动。先把「构建链路」跑通（全量 `// @ts-nocheck`、产物与搬家前等价、83 个测试全过），再分批摘 `@ts-nocheck` 补真类型，两段风险不混。版本迁移期不动，收尾一次性发 1.0.0、打 annotated tag `v1.0.0`。

## 核心决策

1. 目标形态对齐 dsh-dispatcher：源码进 `src/**.ts`，`outDir` 仍是 `lib/`，产物 `lib/**.js` + `lib/index.d.ts`；运行时入口 `lib/index.js` 不变，profile 与 `cordis.patch.yml` 一律不动，插件照旧按包名加载。
2. 所以 `lib/` 从此是构建产物目录：迁移完成后 `lib` 里不许再有手写源码。构建必须关掉 clean/清空行为，只覆盖 src 对应的产物文件，绝不能删 `lib` 里还没搬的旧文件（刀 1 要先实测验证这一点）。

   2.1 **产物不进 git**：`lib/` 是纯构建产物目录，加进 `.gitignore`，不再用 git 跟踪。理由三条：一、迁移期 `lib/*.js` 会从「手写源码」变成「构建产物」，两种性质同目录，git 分不清，搬那一刀的 diff 会变成删 23182 行 + 加 23182 行产物，真正该看的源码搬家被淹掉；二、产物入库后「忘了 build 就 commit」看不出来，源码与产物悄悄不一致，比没有产物更难查；三、仓库只留 `src` 源码，clone 下来的东西是干净的，不给别人看两份同样逻辑。

   配套三条硬要求：`package.json` 加 `"prepare": "tsdown"`，保证 npm/pnpm install 后自动有产物，clone 完不用人记着手动 build；`.gitignore` 加 `lib/`（现在 `lib/` 是被跟踪的，要 `git rm -r --cached lib` 并保留工作区文件），这个动作放在刀 1 里做，因为同一刀 `lib` 正好从源码变产物；另立一条规矩——**切分支、回滚到旧 commit、或从远端拉过代码之后，第一件事是 `npm run build`，否则跑的是本地残留的旧产物**，所有刀的验收里 build 必须是最后一步，这条同步写进 `AGENTS.md`。
3. 测试 83 个 `.mjs` 不改语言、不改 import 路径（继续 import `lib/` 产物），工作流变成「先 build 再 test」；不做 vitest 化，那是另一件事。
4. 分两段风险：先把「构建链路」跑通（全量搬到 `src`、每个文件顶上加 `// @ts-nocheck`、构建产物与搬家前等价、83 个测试全过），再逐批摘 `@ts-nocheck` 补真类型。链路风险和类型风险不许混在一刀里。
5. 类型口径：strict 全开（照 dispatcher 的 tsconfig），迁移期禁止裸 `any`，必须断言的写 `unknown` + 收窄，实在绕不过去的写 `// TODO(ts)` 并集中列清单；每个类型化批次结束 `typecheck` 必须 0 error、`npm test` 全过才提交。
6. 版本号：迁移期不 bump、不打 tag（跟 2026-11-09「大型重构期间本地攒着、不 push、不打 tag」的规矩一致），每刀只 commit 并带票号；全部做完收尾一次性发 1.0.0（0.6.0 → 1.0.0，全量 TS 重写按大版本算），打 annotated tag `v1.0.0`，CHANGELOG 补一段汇总，`v0.6.0` 之后那 17 条无 tag 提交按「历史漏打不补」写进 1.0.0 段，不补中间 tag。
7. 每刀收工都要：`npm run build && npm test` 通过 + `git commit`（带票号）+ 在本文档的进度表里打勾。

## 风险与回滚

最大的坑是 `lib/` 的性质在刀 0–刀 1 之间是混合的（旧的手写 js 还在，新的产物开始往同一目录写）。所以 `clean: false` 不只是省事，是安全前提：tsdown 一 clean 就会先把 `lib` 删空，而插件是 link 安装、dsh-hmr 盯着 `lib/index.js`，删除到重写之间的一次配置重载会 import 到不存在的入口。刀 0 的验收就是实测这一点，刀 1 每一步前后都 `ls lib | wc -l` 看着。

第二风险是打包形态：如果配置误开打包（不带 `unbundle`/`root`），`lib/store.js`、`lib/agents/merge.js` 这些路径会消失，83 个测试里 78 个直接 ENOENT，`memvec` 和 `public` 找 `vec0.so` 的 `../node_modules` 也会跟着错位。所以刀 1 的 diff 校验必须逐文件确认 `lib/**.js` 数量仍是 95。

第三风险是产物不再入库之后的「忘了 build」：切分支、`git reset`、从远端拉完代码，工作区里 `lib/` 可能整个缺失（新 clone）或残留旧产物（回滚）。硬规矩是这些动作之后第一件事 `npm run build`；所有刀的验收里 build 排在最后一步。新 clone 的场景由 `prepare: tsdown` 兜底。

第四风险是 dts：`package.json` 一加 `types`，tsdown 就默认开声明生成（dispatcher 的配置也写着 `dts: true`），但全量 `@ts-nocheck` 阶段生成的 `lib/index.d.ts` 大概率是空壳或直接报错——这一点未实测（见「待定」）。若刀 1 卡在 dts，就把 `dts: false` 撑到刀 8 再打开，最终形态不变。

回滚口径：每一刀单独 commit，回滚就是 `git reset --hard <该刀前一个 commit>` 再 `npm run build`。刀 1 之前 `lib` 还是 tracked，能整块恢复；刀 1 之后 `lib` 不再入库，回滚必须补一次 build，否则跑的是残留产物。任何一刀 `npm test` 不过或产物数量对不上，就地回滚，不带着问题往下走。

## 待定 / 冲突

> 进度表的「备注」列 2026-11-15（t-mwhkwldt-pbja）新增：只记该刀实际覆盖范围与偏离设计的地方，「状态」列只放结论和 commit。

1. **刀 0 验收原话「空 src 能 build 出 lib/index.js」不成立**：tsdown 没有入口会直接报「no entry」并不产出文件。实际验收改成「放一个最小 `src/index.ts` 占位能 build 出 `lib/index.js`」。设计不变，只是验收的输入从空目录改成占位文件。
2. **刀 1 的顺序会拿空 baseline**：方案正文（以及追加的配套顺序）写的是「`git mv` 全部搬完 → `cp -r lib /tmp/lib-baseline`」，但 `git mv` 已经把文件移出 `lib/`，那时 `lib` 里没有东西可拷（只有未搬的产物/残留）。本文按事实改成「先 `cp -r lib /tmp/lib-baseline`，再 `git mv`」，或用 `git archive HEAD lib` 取 HEAD 版本作 baseline。
3. **「产物与搬家前逐个语义等价」不能按字节 diff**：`unbundle` 会重写引号、行宽、`import` 说明符（`.ts` → `.js`），还会补 `export {}` 之类。允许差异的实际判定口径未实测（未查），建议刀 1 实测时定成：`node --check` 每个产物文件 + 逐文件 `diff -w` 人工过一遍 + 83 个测试兜底，并把当次确认的可接受差异清单记进这一节。
